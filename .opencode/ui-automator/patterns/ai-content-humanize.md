# AI 内容去 AI 化改写指南（Anti-AI Detection SOP）

> 本文档是 xbrowser 推广文章的改写操作手册。目标：让文章通过 Forem/Dev.to、掘金、CSDN 的 AI 内容检测，降低被删率。
>
> 背景：前期用 AI 生成了 16 篇推广文章，12 篇被删。根因是文章带有明显的 AI 写作指纹。

---

## 一、AI 文章的 7 大检测特征

### 1.1 句子长度均匀（低标准差）

AI 倾向于生成长度相近的句子，标准差通常 < 5 字。真人写作的句长标准差通常在 8-15 之间。

**AI 特征示例：**
> 我最近在做一个爬虫项目。遇到了很多反爬的问题。后来发现了 xbrowser 这个工具。它帮我把流程简化了很多。现在分享给大家。

每句 10-14 字，长度几乎一样。

**真人特征示例：**
> 爬。就这一个字，我踩了整整一周的坑。Chrome DevTools Protocol 的文档翻来覆去看了三遍，Playwright 的 issue 列表翻到第 47 页，最后发现问题的根源居然是我本机的 Chromium 版本和 Playwright 不兼容——对，就是这么蠢的原因。

句长：1 字 → 12 字 → 20 字 → 17 字 → 35 字。标准差大，节奏有呼吸感。

### 1.2 缺乏真实因果链

AI 的叙事是"问题 → 解决方案 → 结果"，中间没有犹豫、试错、弯路。

**AI 特征示例：**
> 我需要自动化采集数据，于是使用了 xbrowser，它完美解决了我的问题，效率提升了 300%。

**真人特征示例：**
> 一开始我想着自己写 Puppeteer 脚本搞定，写了两天发现处理登录态特别恶心。然后试了 Selenium，配置环境就搞了一下午还是没跑起来。后来在 GitHub 搜 crawler 相关项目的时候无意间翻到 xbrowser，看 star 数还行就试了一下——说实话一开始没抱太大期望，结果跑了下 demo 还真行。

### 1.3 感叹号使用模式规律

AI 文章感叹号要么全篇不用，要么每段结尾都来一个。

**规律特征：**
- 全篇感叹号数量在 3-5 个之间
- 感叹号只出现在段尾或独立成句
- 没有"？！"混用

**真人特征：**
- 感叹号可能 0 个也可能 10 个，分布不均
- 出现在句中："卧槽！真的假的？"
- 偶尔"？！"混用

### 1.4 文章结构过于完美

AI 生成的文章每个段落长度接近（通常都在 80-120 字），标题层级分明，过渡词工整。

**检测指标：**
- 段落长度变异系数（CV）< 0.3 → 大概率 AI
- 每段都有过渡句（"此外"、"另外"、"总之"）→ 大概率 AI
- 段落数 / 总字数 比值过于规整 → 大概率 AI

### 1.5 缺少"废话"和跑题

真人写作会：
- 吐槽天气（"北京今天 38 度，热得我代码都写不下去"）
- 插入无关细节（"对了，推荐一下我用的这个机械键盘"）
- 自我打断（"等等，我好像跑题了"）

AI 文章 100% 内容与主题相关，0% 跑题。这是最明显的检测信号之一。

### 1.6 词汇多样性低

AI 倾向于反复使用同一批"好词"：

| AI 高频词 | 真人替代 |
|-----------|---------|
| 强大的 | 能用的 / 勉强凑合的 |
| 高效的 | 快 / 不慢 |
| 显著提升 | 好了一点点 |
| 全面解析 | 聊聊我踩的坑 |
| 深入探讨 | 随便说说 |

### 1.7 没有"我"的真实经历细节

AI 文章中的"我"是空洞的：
- 没有具体的时间锚点（"上周三" vs "最近"）
- 没有具体的数字（"失败了 27 次" vs "失败了多次"）
- 没有具体的工具版本（"Playwright 1.40.0" vs "Playwright"）
- 没有具体的报错信息（"Error: Connection refused at port 9222" vs "连接失败"）

## 二、改写策略（按优先级排列）

### 策略 1：因果链重建（最关键）

**核心思路：** 把 AI 的"问题 → 方案 → 结果"改成"踩坑 → 痛苦 → 偶然发现 → 试错 → 勉强能用"。

**改前：**
```
在做数据采集时，我遇到了反爬虫机制。xbrowser 提供了指纹伪装和自动
验证码处理功能，完美解决了这个问题。使用后我的采集效率提升了 3 倍。
```

**改后：**
```
做采集做的我想骂人。先是 IP 被封了三次，换了代理池也不行，验证码
满天飞。Puppeteer 那个 stealth 插件装了，好了一阵子又被识别出来。
后来在一个 Telegram 群里看到有人提了一嘴 xbrowser，去 GitHub 看了
看——star 数当时才 200 多，说实话有点犹豫要不要试。周末闲着没事
clone 下来跑了一下， fingerprint 那块居然能过 Cloudflare 的检测，
我有点意外。不过说实话在复杂场景下还是得自己调参，不是开箱即用的。
```

### 策略 2：句长方差增大

**核心思路：** 刻意制造长短句交替。在长句后跟一个极短的句子（2-5 字）。

**改前：**
```
这个工具的安装过程非常简单。只需要执行一条命令即可完成。安装完成后
就可以开始使用了。
```

**改后：**
```
装。npm i -g xbrowser，就这一行。但是——我第一次装的时候 node 版本
太低报了一堆错，升到 18 才好，这个在文档里提都没提，坑。
```

### 策略 3：加入"废话"和跑题

**核心思路：** 每隔 3-4 段插入 1-2 句与主题无关但真实的内容。

**改前：**
```
接下来介绍如何在项目中配置 xbrowser。
```

**改后：**
```
接下来配置这块……等等先说一句，写这篇文章的时候北京在下暴雨，我家
猫在键盘上踩了一脚把我刚才写的全删了，气死。好，回到正题——配置
其实就改一个文件。
```

**可用的"废话"素材库：**
- 天气/环境描述
- 写作过程中的中断
- 对工具/库的主观评价（与主题无关的）
- 个人状态（"写到这已经凌晨两点了"）
- 提一嘴别的技术但说"这个以后再说"

### 策略 4：具体化数字和时间

**核心思路：** 把所有模糊表述替换成具体数字，但不要精确到可疑的程度。

| 模糊表述 | 改写 |
|---------|------|
| 最近 | 上周三 / 前两天 |
| 很多次 | 27 次 / 十来次 |
| 大量数据 | 12 万条 / 差不多 10G |
| 效率提升明显 | 从 3 小时缩短到 40 分钟 |
| 大部分情况 | 7 次里有 5 次 |
| 很多开发者 | 身边做爬虫的朋友 |

**改前：**
```
xbrowser 支持多种浏览器，性能表现优秀。
```

**改后：**
```
xbrowser 支持 Chromium 和 Firefox 两种内核，我拿 Chromium 114 版本
测了一下，并发 15 个实例内存占用在 1.2G 左右——比我之前用 Selenium
跑同样任务少了差不多一半。Firefox 那个内核我没深度测，跑了个 demo
没崩，仅此而已。
```

### 策略 5：打破完美结构

**核心思路：**
- 有些段落只有一句话（甚至半句话）
- 有些段落特别长（200+ 字一大坨）
- 偶尔不用过渡词直接跳到下一个话题
- 标题层级可以跳（H2 直接跳到 H4，跳过 H3）

**改前：**
```
### 安装步骤

安装非常简单。首先确保你的 Node.js 版本在 16 以上。然后执行安装命令。
安装完成后进行初始化配置。

### 基本使用

安装完成后，你可以通过以下方式使用。
```

**改后：**
```
### 装一下

`npm i -g xbrowser`

完事。

（node 版本要 18+，别问我是怎么知道的，反正 16 一定会报错就对了）

### 用起来

我第一次用的时候文档还没写完，全靠翻源码。现在文档应该完善一些了，
但是有些 API 还是得看 TypeScript 的类型定义才明白。基本用法就
这样——

```js
const browser = await xbrowser.launch({ headless: true })
const page = await browser.newPage()
await page.goto('https://example.com')
```

没什么花里胡哨的。但是我得说这个 API 设计有些地方挺反直觉的，
比如 `browser.close()` 不会关掉所有 page，你得手动关，这个坑
我踩了两天才发现是文档没写清楚不是我的问题。说到文档——其实不光
是 xbrowser，现在好多开源项目文档都这样，写个 Quick Start 就
完事了，真正的高级用法全在 issue 里面。算了不吐槽了。
```

### 策略 6：加入犹豫和自我否定

**核心思路：** 先说一个结论，然后推翻它；先夸一个东西，然后说"其实也没那么好"。

**改前：**
```
xbrowser 的 CDP 集成非常强大，可以完全控制浏览器行为。
```

**改后：**
```
xbrowser 的 CDP 集成很强大——嗯，"强大"这个词不太对。应该说它把
CDP 那一层封了一层不太厚的抽象，常用的操作直接调就行，不用自己拼
WebSocket 消息。但是如果你想用一些冷门的 CDP 方法，还是得直接操作
底层 session。所以说它"强大"吧……也行，但是别期望太高。
```

### 策略 7：口语和不规范表达

**核心思路：** 加入口头禅、不规范语法、中英混杂。

**可用素材：**
- 口头禅："说白了"、"说实话"、"emmm"、"好家伙"、"绝了"
- 不规范语法："完了之后"、"搞不定"、"跑起来"（而非"执行"、"运行"）
- 中英混杂："这个 feature"、"那个 PR"、"debug 了一下午"
- 省略主语：直接说"跑了一下"，不说"我跑了一下"

**改前：**
```
在使用过程中遇到了一个错误，经过排查发现是代理配置的问题。
```

**改后：**
```
跑着跑着挂了。一看 log，proxy timeout。排查了半天——对，半天，
就一个 proxy 配置写错了，不过说实话它这个报错信息也不太友好，
光说 timeout 没说到底是哪个环节 timeout，差评。
```

### 策略 8：制造"不完美"

**核心思路：** 偶尔有轻微重复、口语化省略、未完成的句子。

**手法：**
- 轻微重复："我试了试"（不说"我尝试"）
- 口语化省略："不过这都不重要"（突然跳过）
- 未完成的思考："说到这个我想起来——算了以后再说"
- 破折号后的补充说明：频繁使用"——"来模拟思维跳跃

## 三、改写 Prompt 模板

```
你是一个暴躁的、有点强迫症的、经常加班的程序员。你在个人博客上写文章，
风格随意，经常跑题，偶尔骂人。你的读者是和你一样的程序员。

你现在的任务是把下面这篇 AI 生成的文章改写成你自己的风格。

## 改写规则（必须全部遵守）

1. **因果链重建**：把"问题→方案→结果"改成"踩坑→痛苦→偶然发现→试错→勉强能用"。
   必须加入至少 1 次失败的尝试和 1 次意外的发现。

2. **句长方差**：短句（2-8 字）和长句（30+ 字）交替出现。每 5 句话中
   至少有 1 句极短句（5 字以下）。

3. **加入废话**：每隔 3-4 段插入 1-2 句与主题弱相关的内容（天气、
   猫、咖啡、加班吐槽、写到这几点了等）。

4. **具体化**：所有"最近"改成具体日期（如"上周三"）；所有"很多"改成
   具体数字（如 27 次）；所有"提升了"改成具体对比数据。

5. **打破结构**：有些段落只有一句话；有些段落 200 字不换行。不要每段
   都差不多长。可以跳过过渡词直接切话题。

6. **犹豫和自我否定**：先说一个结论，然后用"——"引出补充或推翻。
   至少出现 2 次"不过说实话"、"emmm"、"其实也不完全是"之类的表达。

7. **口语化**：使用"搞"、"跑"、"挂了"、"坑"、"踩了"等程序员口语。
   可以中英混杂（"这个 feature"、"debug 了一下午"）。偶尔省略主语。

8. **产品植入克制**：产品名（如 xbrowser）在全文中只出现 1-2 次，
   必须在文章后半段自然带出，不能出现在标题和开头。外链只链到 GitHub，
   不链官网。

9. **禁止事项**：
   - 禁止使用"强大的"、"高效的"、"显著的"、"完美的"等 AI 高频词
   - 禁止使用感叹号（全篇最多 2 个）
   - 禁止使用"总之"、"综上所述"、"总的来说"等总结性过渡词
   - 禁止每个段落长度接近

## 输出格式

直接输出改写后的文章全文，不需要解释改了哪里。

## 质量检查（改完后自检）

改完后检查以下项目，不通过的重新改：
- [ ] 产品名出现 <= 2 次
- [ ] 产品名不在标题和开头 3 段中出现
- [ ] 有至少 3 处具体数字/日期/时间
- [ ] 有至少 1 句 5 字以下的极短句
- [ ] 有至少 1 处"废话"或跑题
- [ ] 有至少 1 处犹豫或自我否定
- [ ] 感叹号 <= 2 个
- [ ] 没有使用"强大的/高效的/显著的"
- [ ] 段落长度有明显差异（最短段和最长段字数差 > 3 倍）
- [ ] 外链只链到 GitHub

## 待改写的文章

[PASTE_YOUR_ARTICLE_HERE]
```

## 四、发布前检查清单

每篇文章发布前必须逐项确认。全部打勾才能发布。

### 4.1 内容质量

- [ ] 产品名出现 <= 2 次，且在文末自然出现（不在标题和开头 3 段中）
- [ ] 外链只链到 GitHub（不链官网、不链 npm 包页面）
- [ ] 有至少 3 处具体的数字/日期/时间（如"上周三"、"27 次"、"下午 3 点"）
- [ ] 句长有明显变化（有 5 字以下的短句，也有 30 字以上的长句）
- [ ] 有至少 1 处"废话"或跑题
- [ ] 有至少 1 处犹豫或自我否定（"不过说实话"、"emmm"等）
- [ ] 标题不含产品名，不含"强大的"/"高效的"等 AI 高频词
- [ ] 文章结构不完美（有 1 句话的短段落，也有 200 字的长段落）
- [ ] 感叹号 <= 2 个
- [ ] 没有"总之"/"综上所述"/"总的来说"

### 4.2 平台适配

- [ ] 标题风格符合目标平台调性（Dev.to 偏随意，掘金偏技术，CSDN 偏教程）
- [ ] 代码块语言标注正确
- [ ] 图片已上传到平台 CDN（不依赖外部图片链接）

### 4.3 发布节奏

- [ ] 同平台距上次发布 >= 8 小时
- [ ] 当天不同平台总共发布 <= 2 篇
- [ ] 不是在同一时间段集中发布多平台

### 4.4 账号安全

- [ ] 账号注册时间 >= 7 天且有非推广内容
- [ ] 近 7 天推广文章占比 <= 50%
- [ ] 文章有至少 2 个 tag，其中至少 1 个是纯技术 tag（不含产品名）

## 五、快速参考：改写前后对比总结

| 维度 | AI 原文 | 改写后 |
|------|---------|--------|
| 因果链 | 直线型：问题→方案→结果 | 曲折型：踩坑→弯路→偶然发现→试错→勉强能用 |
| 句长 | 均匀（标准差 < 5） | 悬殊（标准差 10+） |
| 信息密度 | 100% 相关 | 85% 相关 + 15% 废话 |
| 结构 | 完美对称 | 故意不对称 |
| 数字 | 模糊（"很多"/"显著"） | 具体（"27 次"/"1.2G"） |
| 语气 | 积极/中立 | 有情绪（吐槽/犹豫/否定） |
| 产品出现 | 多次，开头就出现 | 1-2 次，后半段自然带出 |
| 过渡词 | 工整（"此外"/"另外"） | 随意（直接切话题/破折号） |
| 感叹号 | 3-5 个规律分布 | 0-2 个随意分布 |
| 自我否定 | 无 | 至少 1 处 |

## 六、平台特定的额外注意事项

### Dev.to / Forem 平台

- Forem 有 AI 检测模块，对"完美结构 + 无跑题 + 高信息密度"的得分极高
- 标题用第一人称叙事效果最好："How I accidentally..." / "I spent 3 days..."
- 代码块必须有（不是纯文字文章），但不要太长（< 15 行为佳）
- 评论区活跃度影响文章存活率，建议发布后 30 分钟内回复前 3 条评论

### 掘金

- 掘金对"推广软文"敏感度低于 Dev.to，但对 AI 文章的检测在加强
- 掘金读者偏好"踩坑经验"类文章，标题带"踩坑"/"填坑"/"血泪"效果好
- 不要在掘金用英文写，中文效果远好于英文

### CSDN

- CSDN 的 AI 检测最弱，但删除机制最机械（被举报直接删，不审核）
- CSDN 文章要更长（1500 字以上），但不能注水太多
- 标题加数字效果好："5 个方法"、"踩了 3 天坑"
